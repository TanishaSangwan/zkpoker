## Findings

[P0] **1. `privacy_invoke`'s pool-authorization check is self-referential and bypassable**

`Class: UNTRUSTED_CALLBACK_CALLER` · `cairo/src/lib.cairo:319-344` (pre-fix) · Confidence: 96 · Severity: Critical

**Description**
`privacy_invoke` is documented as callable only by the trusted STRK20 pool, enforced by `assert(pool_address == caller, errors::BAD_POOL)` — but `pool_address` is a caller-supplied parameter, not a value read from storage; there is no `pool_address` field anywhere in `Storage` and no constructor. Any address can call `privacy_invoke(token, pool_address: <itself>, note_id)` and trivially satisfy the check. If `pending_payout[note_id]` is nonzero, the function zeroes it and calls `erc20.approve(pool_address, owed)` — approving the attacker's own address to pull `owed` tokens out of the contract's real balance via `transferFrom`. `get_pending_payout` is a public view, so an attacker can also front-run the *real* pool's honest call for a legitimately-settled winner and steal their payout first. Independently confirmed by three of the four scanning agents (Access-Control, External-Calls, Storage/Trust partitions), each converging on the same root cause. `token` is likewise never validated against the note's originating table, so the fix also binds payouts to a specific token, not just a pinned pool address.

**Status: FIXED.** Added a `#[constructor]` pinning `pool: ContractAddress` in storage; `privacy_invoke` now asserts `caller == self.pool.read()` and `token == self.payout_token.entry(note_id).read()`, and approves `self.pool.read()` rather than the caller-supplied argument.

**Required Tests**
- Regression: a non-pool address calls `privacy_invoke` passing its own address as `pool_address` on a note with nonzero `pending_payout`; assert it reverts with `BAD_POOL`.
- Guard: only the deployed `pool` address can successfully call `privacy_invoke`, and the approved spender is always `self.pool.read()` regardless of the `pool_address` argument.
- Regression: `privacy_invoke` called with a `token` that doesn't match the note's recorded `payout_token` reverts with `BAD_TOKEN`.

[P0] **2. No caller/dealer check on `settle_table` (and every other game-state entrypoint) lets anyone fabricate and redirect a table's pot**

`Class: V6` · `cairo/src/lib.cairo:238, 283-317` (pre-fix) · Confidence: 92 · Severity: Critical

**Description**
`settle_table` validated only that the table exists and that `winners`/`payout_note_ids` were equal-length and non-empty — it never checked the caller was the table's creator/dealer, and never validated that `payout_note_ids[i]` actually corresponded to `seat_note[(table_id, winners[i])]`. `bet` had the same gap: it only performs a storage write (`table_pot += amount`) with no real token transfer or seat-ownership check, so a table's recorded pot is pure bookkeeping disconnected from actual deposits. Chained: an attacker could call `create_table` for a fresh table, `bet(table_id, seat, huge_amount)` to inflate the pot with zero real funds, then `settle_table(table_id, winners=[x], payout_note_ids=[attacker_note])` to route that fabricated amount into `pending_payout` for a note they control — which Finding 1 then let them redeem directly against the contract's *real* pooled balance from other, legitimate tables. The identical missing-caller-check pattern also affects `join_table`, `commit_deal`, `mark_dealt`, `reveal_seed`, `bet`, and `fold` (still true post-fix — see "Still open" below).

**Status: PARTIALLY FIXED.** `create_table` now records the caller as `table_dealer`; `settle_table` asserts the caller is that dealer, and asserts each `payout_note_ids[i]` matches `seat_note[(table_id, winners[i])]` before crediting it.

**Still open:** `bet`, `fold`, `join_table`, `commit_deal`, `mark_dealt`, and `reveal_seed` still have no per-seat/per-dealer caller check — `bet` in particular still records amounts with no on-chain link to a real transfer. The pool's own deposit flow must remain the source of truth for what a table legitimately holds until seat-level authorization is designed (see `docs/DESIGN.md` "Open items").

**Required Tests**
- Regression: a non-dealer address calls `settle_table` on a table it didn't create; assert it reverts with `NOT_DEALER`.
- Regression: the dealer calls `settle_table` with `payout_note_ids` not matching `seat_note` for the given `winners` seats; assert it reverts.
- Guard: the dealer settles with correct seat/note pairs and the pot splits and pays out as expected.

[P1] **3. Cross-function reentrancy window: `balance_of` executes before `pending_payout` is finalized, against fully unguarded entrypoints**

`Class: CROSS_FUNCTION_REENTRANCY` · `cairo/src/lib.cairo:331-337` (pre-fix) · Confidence: 78 · Severity: High

**Description**
Inside `privacy_invoke`, `erc20.balance_of(get_contract_address())` — an external call to an address supplied via the caller-controlled `token` parameter — executed while `pending_payout.entry(note_id)` still held its pre-payout value; the write to zero only happened after this call returned. None of the contract's other state-mutating entrypoints carried a reentrancy guard.

**Status: FIXED (for `privacy_invoke`).** Added a `reentrancy_lock: bool` in storage, set at entry to `privacy_invoke` and cleared at exit. `bet`/`settle_table`/`create_table` are not separately locked — see Finding 2's "Still open".

**Required Tests**
- Regression: a mock ERC20 whose `balance_of` calls back into `privacy_invoke` (directly, or via `settle_table` once that's also locked) asserts the reentrant call reverts with `REENTRANCY`.

[P2] **4. Integer-division remainder in `settle_table` permanently locked pot dust**

`Class: ROUNDING-FUND-LOCK` · `cairo/src/lib.cairo:296-317` (pre-fix) · Confidence: 80 · Severity: Medium

**Description**
`settle_table` computed `share = pot / winners.len()` and credited `share` to each winner, then unconditionally zeroed `table_pot`. Whenever `pot` wasn't an exact multiple of `winners.len()`, the remainder was never credited anywhere and was stranded in the contract's balance with no map entry, getter, or function that could ever reference it again.

**Status: FIXED.** The remainder (`pot - share * winners.len()`) is now added to the first winner's payout in the same loop.

**Required Tests**
- Regression: settle a table with `pot=100`, `winners.len()=3`; assert the total credited across `pending_payout` equals `100`.
- Guard: sum of `pending_payout` deltas equals pre-settlement `table_pot` across a range of pot/winner-count combinations.

[P3] **5. `approve()` return value ignored after `pending_payout` is already cleared**

`Class: UNCHECKED_EXTERNAL_CALL_RETURN` · `cairo/src/lib.cairo:339` (pre-fix) · Confidence: 70 · Severity: Low

**Description**
`privacy_invoke` clears `pending_payout` and then calls `erc20.approve(...)` without checking the returned `bool`. For a non-conforming ERC20 that returns `false` on failure instead of reverting, the payout accounting is already zeroed before the failure is observable.

**Status: NOT FIXED** (below confidence threshold — no fix block required per the audit skill's report format, but worth a follow-up before mainnet).
