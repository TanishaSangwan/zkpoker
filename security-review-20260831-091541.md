## Findings

[P2] **1. Unchecked `approve()` return value in `privacy_invoke` can permanently strand a winner's payout**

`Class: UNCHECKED-EXTERNAL-RETURN` · `cairo/src/lib.cairo` (`privacy_invoke`) · Confidence: 78 · Severity: Medium

**Description**
This exact gap was flagged every round since round 1, always scored just below the 75 confidence threshold — round 5 is the first to score it above. `create_table` pins `table_token` to any caller-supplied address with no allowlist (anyone calling `create_table` is an unvetted "dealer"). In `privacy_invoke`, once `pending_payout[note_id]` is zeroed, `erc20.approve(self.pool.read(), owed.into())` is called and its boolean result discarded, then `Invoked` is unconditionally emitted as if the payout succeeded — the same pattern already guarded for `transfer_from` (in `bet`) and `transfer` (in `reclaim_stalled_bet`), but left unguarded here. A token whose `approve()` returns `false` instead of reverting (while `transfer_from`/`balance_of` behave normally, so real bets land fine) lets a winner's payout be marked paid with no real allowance ever granted — permanently unrecoverable, since `pending_payout` is already 0 and `reclaim_stalled_bet` is blocked by `table_settled`.

**Status: FIXED.** `privacy_invoke` now asserts the `approve()` return value, reverting with `TRANSFER_FAILED` on `false`.

**Required Tests**
- A mock ERC20 whose `approve()` returns `false` without reverting: run a full create/join/bet/settle/`privacy_invoke` flow and confirm it now reverts with `TRANSFER_FAILED` instead of zeroing `pending_payout` with no real allowance granted.
- Guard test: a normal ERC20 whose `approve()` returns `true` still succeeds as before.
