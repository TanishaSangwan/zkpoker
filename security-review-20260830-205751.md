## Findings

[P0] **1. `payout_token` overwrite lets a self-dealt table relabel an accumulated `note_id` payout into a different, valuable token**

`Class: MULTI_TOKEN_ACCOUNTING_MISMATCH` · `cairo/src/lib.cairo` (`settle_table`) · Confidence: 90 · Severity: Critical

**Description**
`note_id_owner` (round 2's fix) only checks that the *same address* re-registers a `note_id` across tables — it says nothing about the *token*. `settle_table` unconditionally overwrote `payout_token[note_id]` on every settlement call, while `pending_payout[note_id]` is purely additive. Attack: register `note_id N` at your own Table A using a worthless self-minted/self-controlled token, bet and settle a large fabricated `pending_payout[N]` there; then register the *same* `N` at Table B using a real token, and settle Table B too — even with a zero pot, since the overwrite was unconditional. `payout_token[N]` would then point at the real token while the large fabricated balance from Table A remained, and `privacy_invoke` would pay that fabricated amount out of the contract's real, shared balance.

**Status: FIXED.** `settle_table` now asserts `existing_pending == 0 || existing_token == token` before (re)writing `payout_token[note_id]` — a note_id's payout token can only be set once a nonzero balance exists for it, unless the new token matches.

**Required Tests**
- Regression: settle `note_id N` at Table A (token X, nonzero pot); settle a second table for the same `note_id` at Table B (token Y, any pot); assert the second `settle_table` call reverts with `BAD_TOKEN`.
- Guard: settling two tables sharing the same token for the same `note_id` still accumulates `pending_payout` correctly and pays out once via `privacy_invoke`.

[P0] **2. Dealer-abandoned table permanently locks real bettor funds — no recovery path**

`Class: ACCESS_CONTROL_NO_RECOVERY` (escalated from Low in round 2) · `cairo/src/lib.cairo` (`table_dealer`/`settle_table`) · Confidence: 88 · Severity: Critical

**Description**
`table_dealer` is set once at `create_table` and never reassignable; `settle_table` (the only function that ever cleared `table_pot`) was gated to that fixed dealer with no timeout, admin override, or alternate path. In round 2 this was a below-threshold hardening note because `bet()` didn't move real funds yet. Round 2's `bet()` fix (real `transfer_from`) changed the risk: an abandoned/malicious dealer could permanently lock real bettor funds with zero recourse.

**Status: FIXED — timeout-based self-refund (user's choice among 3 options).**
- New storage: `table_created_at` (set in `create_table`), `seat_contributed` (incremented in `bet()` with the *actual received* amount, not the nominal one), `table_settled` (set `true` at the end of `settle_table`, blocking reclaim after a hand legitimately resolved).
- New entrypoint `reclaim_stalled_bet(table_id, seat)`: the seat's own owner can pull back exactly what they personally contributed once `get_block_timestamp() >= table_created_at + SETTLE_TIMEOUT_SECS` (24h) and the table isn't `table_settled`. Takes the shared `reentrancy_lock`; writes state (zeroing `seat_contributed`, decrementing `table_pot`) before the external `transfer` call.
- Added `IErc20::transfer` (only `approve`/`balance_of`/`transfer_from` existed before), errors `TOO_EARLY`/`ALREADY_SETTLED`, event `Reclaimed`.
- The other two options considered (pool-level force-settle; accept-and-document for the demo) were not chosen — noted here for context if revisited.

**Required Tests**
- A table with real bet funds whose dealer goes silent past 24h: each seat can reclaim its own contribution via `reclaim_stalled_bet`.
- A live/settled table cannot have its pot reclaimed (`ALREADY_SETTLED`); a seat cannot reclaim before the timeout (`TOO_EARLY`) or reclaim twice (second call reverts on `owed != 0`).

[P1] **3. Unguarded external call + CEI violation in `bet()` allows malicious-token reentrancy**

`Class: REENTRANCY-CEI` · `cairo/src/lib.cairo` (`bet()`) · Confidence: 80 · Severity: High

**Description**
`bet()`'s `transfer_from` call (round 2's fix) ran against a caller-chosen `token` (pinned once at `create_table`, no allowlist), with `table_pot` credited only *after* the call returned and no reentrancy lock. A malicious `token`'s `transfer_from` could reenter `bet`/`fold`/`join_table` mid-call, satisfying `seat_owner`/`table_dealer` checks for any table/seat the attacker's own contract already controls. (Confirmed not reachable: reentering `privacy_invoke` itself — its caller check would see the token contract, never the pinned `pool`.)

**Status: FIXED.** `bet()` now takes the shared `reentrancy_lock` for its full body (any nested `bet`/`privacy_invoke` call reverts with `REENTRANCY`).

**Required Tests**
- A mock token whose `transfer_from` re-enters `bet()` on the same table/seat must revert with `REENTRANCY`.
- A mock token returning `false` from `transfer_from` must revert the whole `bet()` call with `TRANSFER_FAILED`, leaving `table_pot`/`seat_contributed` unchanged.

[P2] **4. `bet()` trusts nominal `amount` instead of measuring actual received balance**

`Class: TOKEN-ACCOUNTING-DRIFT` · `cairo/src/lib.cairo` (`bet()`) · Confidence: 76 · Severity: Medium

**Description**
`bet()` credited `table_pot` with the literal `amount` parameter after `transfer_from` succeeded, without checking the actual balance delta. A fee-on-transfer/deflationary token would deliver less than `amount` per bet while `table_pot`/`pending_payout` recorded the full nominal amount — invisible until `privacy_invoke`'s balance check started failing for that token.

**Status: FIXED.** `bet()` now reads `balance_of(contract)` before and after `transfer_from`, and credits `table_pot`/`seat_contributed`/the `Bet` event with the measured delta, not the nominal `amount`.

**Required Tests**
- A mock fee-on-transfer token (delivers e.g. 98% of `amount`): `table_pot` must reflect only the actually-received delta, not the nominal amount.
