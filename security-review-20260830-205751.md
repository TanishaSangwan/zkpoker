## Findings

[P0] **1. `payout_token` overwrite lets a self-dealt table relabel an accumulated `note_id` payout into a different, valuable token**

`Class: MULTI_TOKEN_ACCOUNTING_MISMATCH` · `cairo/src/lib.cairo` (`settle_table`, the `payout_token.entry(note_id).write(token)` line) · Confidence: 90 · Severity: Critical

**Description**
`note_id_owner` (round 2's fix) only checks that the *same address* re-registers a `note_id` across tables — it says nothing about the *token*. `settle_table` unconditionally overwrites `payout_token[note_id]` on every settlement call, while `pending_payout[note_id]` is purely additive. Attack: register `note_id N` at your own Table A using a worthless self-minted/self-controlled token, bet and settle a large fabricated `pending_payout[N]` there; then register the *same* `N` at Table B using a real token (e.g. the token real players use), and settle Table B too — even with a zero pot, since the overwrite is unconditional. `payout_token[N]` now points at the real token while the large fabricated balance from Table A remains. `privacy_invoke(real_token, N)` then pays that fabricated amount out of the contract's real, shared balance for that token — draining funds that belong to unrelated legitimate players. Zero privilege required; the attacker only needs to be dealer of their own two throwaway tables.

**Fix** (agreed shape, not yet applied)

```diff
                 let seat = *winners.at(i);
                 assert(self.seat_note.entry((table_id, seat)).read() == note_id, errors::NO_TABLE);
                 assert(
                     self.note_id_owner.entry(note_id).read() == self.seat_owner.entry((table_id, seat)).read(),
                     errors::NOTE_ID_TAKEN,
                 );
+                let existing_pending = self.pending_payout.entry(note_id).read();
+                let existing_token = self.payout_token.entry(note_id).read();
+                assert(existing_pending == 0 || existing_token == token, errors::BAD_TOKEN);
                 self.payout_token.entry(note_id).write(token);
```

**Required Tests**
- Regression: settle `note_id N` at Table A (token X, nonzero pot); settle a second table for the same `note_id` at Table B (token Y, any pot including zero); assert the second `settle_table` call reverts with `BAD_TOKEN` instead of silently relabeling the pending amount.
- Guard: settling two tables that share the *same* token for the same `note_id` still accumulates `pending_payout` correctly and pays out once via `privacy_invoke`.

[P0] **2. Dealer-abandoned table permanently locks real bettor funds — no recovery path**

`Class: ACCESS_CONTROL_NO_RECOVERY` (escalated from Low in round 2) · `cairo/src/lib.cairo` (`table_dealer` binding in `create_table`; dealer-only gate in `settle_table`) · Confidence: 88 · Severity: Critical

**Description**
`table_dealer` is set once at `create_table` and never reassignable; `settle_table` (the only function that ever clears `table_pot`) is gated to that fixed dealer, with no timeout, admin override, or alternate path. In round 2 this was a below-threshold hardening note because `bet()` didn't move real funds yet — an abandoned table stranded nothing real. Round 2 fixed `bet()` to pull real funds via `transfer_from`. That fix changed the risk: any address can permissionlessly `create_table`, become its dealer, accept players who `join_table` + `bet` real funds, then simply never call `settle_table` (malice, going offline, or a client bug) — permanently locking those real funds with zero recourse anywhere in the contract.

**Fix — NOT YET DECIDED.** This needs a product decision before implementing (see `HANDOFF.md` "Pending decision"). Candidate shapes discussed:
- **Timeout-based self-refund** (each agent's default recommendation): add `table_created_at: Map<felt252, u64>` (set via `get_block_timestamp()` in `create_table`) and `seat_contributed: Map<(felt252, felt252), u128>` (incremented in `bet()`), plus a `table_settled: Map<felt252, bool>` flag (set `true` at the end of `settle_table`, to block reclaiming after a hand legitimately resolved — a losing seat's contribution became the winner's payout, not something to refund). A new `reclaim_stalled_bet(table_id, seat)` entrypoint lets the seat's own owner pull back exactly what they personally contributed once `get_block_timestamp() >= table_created_at + SETTLE_TIMEOUT_SECS` (a constant, e.g. 24h) and `!table_settled`. Needs `IErc20::transfer` added (only `approve`/`balance_of`/`transfer_from` exist today) and new errors `TOO_EARLY` / `ALREADY_SETTLED`.
- **Pool-level force-settle override**: let the pinned `pool` address force a settlement/refund on any table after a timeout instead of per-seat self-refund. Fewer new storage fields, but gives `pool` a new privileged power over every table — a bigger trust-model change.
- **Accept and document for the hackathon demo**: note the risk explicitly (tables are expected to be short-lived and the "dealer" is the app's own backend in the intended usage, not an arbitrary untrusted third party) and revisit before any real deployment.

**Required Tests** (once a shape is chosen): a table with real bet funds whose dealer goes silent past the timeout — funds must become recoverable (self-refund) or forcibly settleable (pool override), and a live/actively-settled table must not be prematurely reclaimable, with no double-reclaim possible per seat.

[P1] **3. Unguarded external call + CEI violation in `bet()` allows malicious-token reentrancy**

`Class: REENTRANCY-CEI` · `cairo/src/lib.cairo` (`bet()`, the `transfer_from` call and the `table_pot` write after it) · Confidence: 80 · Severity: High

**Description**
`bet()`'s `transfer_from` call (round 2's fix) runs against `token = table_token[table_id]`, a value pinned once by whoever called `create_table` with no allowlist. `table_pot` is only credited *after* this external call returns, and `bet()` takes none of the `reentrancy_lock` that guards `privacy_invoke`. A caller who is dealer of their own table can set `table_token` to a malicious contract and have its `transfer_from` re-enter `bet`/`fold`/`join_table` mid-call — the nested call's `get_caller_address()` resolves to the malicious contract itself, satisfying `seat_owner`/`table_dealer` checks for any table/seat it already controls. (Confirmed *not* reachable: reentering `privacy_invoke` itself — its caller check would see the token contract, which can never equal the pinned `pool` address.)

**Fix** (agreed shape, not yet applied): reorder to checks-effects-interactions — credit `table_pot` *before* the external `transfer_from` call — and have `bet()` take the existing `reentrancy_lock` too (with `assert(transferred, ...)` still enforced; a failed transfer must revert the whole call, including the now-earlier state write).

**Required Tests**
- A mock token whose `transfer_from` re-enters `bet()`/`join_table` on the same table/seat before returning must revert with the reentrancy guard once fixed (and be shown to currently succeed/double-process pre-fix).
- A mock token returning `false` from `transfer_from` must still revert the whole `bet()` call with `TRANSFER_FAILED`, leaving `table_pot` unchanged.

[P2] **4. `bet()` trusts nominal `amount` instead of measuring actual received balance**

`Class: TOKEN-ACCOUNTING-DRIFT` · `cairo/src/lib.cairo` (`bet()`) · Confidence: 76 · Severity: Medium

**Description**
`bet()` credits `table_pot` with the literal `amount` parameter after `transfer_from` succeeds, without checking the contract's actual balance delta. A fee-on-transfer/deflationary token chosen as a table's currency (nothing stops this at `create_table`) would deliver less than `amount` per bet while `table_pot`/`pending_payout` record the full nominal amount — invisible until `privacy_invoke`'s balance check starts failing for that token, at which point some legitimate winners become unpayable.

**Fix** (agreed shape, not yet applied): read `balance_of(contract)` before and after the `transfer_from` call and credit `table_pot` with the actual delta, not the nominal `amount`.

**Required Tests**
- A mock fee-on-transfer token (delivers e.g. 98% of `amount`) must, pre-fix, show `table_pot` credited the full nominal amount despite the shortfall; post-fix, `table_pot` must reflect only the actually-received delta.
