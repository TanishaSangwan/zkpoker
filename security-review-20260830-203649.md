## Findings

[P0] **1. Cross-table `note_id` collision lets any player hijack another player's `payout_token`/`pending_payout`**

`Class: CROSS_TABLE_NOTE_ID_COLLISION` · `cairo/src/lib.cairo:187-189, 297, 399-403` (pre-fix) · Confidence: 90 · Severity: Critical

**Description**
`pending_payout` and `payout_token` are keyed only by bare `note_id`, with no `table_id` discriminator. `join_table` let any caller supply an arbitrary `hole_card_note_id` with zero validation that it actually belonged to them. Since `create_table`/`join_table` are fully permissionless, an attacker could create their own throwaway table, join it using a victim's real `note_id` copied from the victim's unrelated, legitimate table, name themselves the winner of their own table, and call `settle_table`. `settle_table`'s existing seat/note check only verified consistency *within the attacker's own table* — it did nothing to stop reuse of a `note_id` that already belonged to someone else's pending payout. This overwrote the victim's `payout_token[note_id]` to a token the attacker chose and merged the attacker's (even zero) pot into the victim's `pending_payout[note_id]`, permanently freezing the victim's already-won funds once the real token stopped matching. Independently confirmed by a second partition (Math/Economics), which additionally noted the same-account variant (joining two of your own tables with the same `note_id` corrupts your own payout) and the composability with Finding 2 (consolidating several fabricated pots onto one `note_id` before draining it).

**Status: FIXED.** Added a `note_id_owner: Map<felt252, ContractAddress>`. `join_table` binds a `note_id` to whoever registers it first (or asserts the same caller on reuse); `settle_table` asserts `note_id_owner[note_id] == seat_owner[(table_id, seat)]` before honoring a payout.

**Required Tests**
- Regression: attacker joins a self-created table with a `note_id` already owned by a victim elsewhere, settles as winner; assert the call reverts with `NOTE_ID_TAKEN` post-fix (and demonstrate the corruption pre-fix).
- Guard: a second `join_table` reusing an already-owned `note_id` from a different account reverts with `NOTE_ID_TAKEN`; the same account reusing its own `note_id` across tables still succeeds.

[P0] **2. `bet()` credited `table_pot` with no real value transfer — pot fabrication survived the `seat_owner` fix**

`Class: ACCOUNTING-UNBACKED-VALUE` · `cairo/src/lib.cairo:347-357` (pre-fix) · Confidence: 85 · Severity: Critical

**Description**
The `seat_owner` fix closed only the *impersonation* angle. `create_table`/`join_table` are permissionless, so an attacker could be both the dealer and the sole seat-owner of their own table, then call `bet(table_id, seat, amount)` with an arbitrary `amount` — the function only did `table_pot += amount`, with no `transfer_from`, balance check, or allowance check. The attacker could then call `settle_table` (dealer-only, but they are the dealer) naming themselves the winner, moving the fabricated amount into `pending_payout` bound to the table's real token. `privacy_invoke`'s only backstop was `balance_u128 >= owed` against the contract's **total** ERC20 balance for that token — an aggregate shared with every other legitimate table using it — so a sufficiently funded pool (from honest players elsewhere) would pay out the fabricated amount.

**Status: FIXED.** `IErc20` gained `transfer_from`; `bet` now calls `erc20.transfer_from(caller, get_contract_address(), amount)` and asserts success before crediting `table_pot`.

**Required Tests**
- Regression: attacker creates a table, joins their own seat, calls `bet()` with a large amount and no prior `approve`; assert it reverts with `TRANSFER_FAILED` post-fix (and demonstrate the drain pre-fix against an unrelated table's real deposits).
- Guard: `bet()` succeeds and correctly moves tokens when the caller has approved this contract for at least `amount`.

[P2] **3. No recovery path for dealer/pool roles — funds can be permanently stranded**

`Class: ACCESS_CONTROL_NO_RECOVERY` · `cairo/src/lib.cairo:172, 196, 288` · Confidence: 70 · Severity: Medium

**Description**
`table_dealer` is fixed forever at `create_table`, and `pool` is fixed forever at construction — no grant/rotate/revoke path exists for either. A dealer who goes offline or withholds `settle_table` after players have funded a table leaves that pot permanently unclaimable, and a `pool` that needs to point at a redeployed pool contract can never be updated.

**Status: NOT FIXED** (below confidence threshold; tracked in `docs/DESIGN.md`).

[P3] **4. Constructor accepts `pool` address with no non-zero validation**

`Class: CONSTRUCTOR_ZERO_ADDRESS` · `cairo/src/lib.cairo:194-197` · Confidence: 60 · Severity: Low

**Description**
